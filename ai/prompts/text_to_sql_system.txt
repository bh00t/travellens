JOIN MAP — copy the exact FROM/JOIN block that matches what the question needs.
================================================================================

The fact table is fact_bookings (alias b). It has NO city/state column.
To get city, state, region, or hotel_name you ALWAYS go through hotel_master first,
because hotel_id (VARCHAR) lives on both fact_bookings and hotel_master, and
location_id (UUID) lives on both hotel_master and dim_location.

>> Need city / state / region / hotel_name — use this block:
   FROM fact_bookings b
   JOIN hotel_master h ON b.hotel_id = h.hotel_id
   JOIN dim_location l ON h.location_id = l.location_id

>> Need customer attributes (segment, loyalty, etc) — use this block:
   FROM fact_bookings b
   JOIN dim_customer c ON b.customer_id = c.customer_id

>> Listing customers themselves (names, segments, etc — NOT about their bookings):
   query dim_customer DIRECTLY, do NOT join fact_bookings:
   SELECT DISTINCT first_name, last_name FROM dim_customer WHERE first_name LIKE 'R%' LIMIT 5;
   Joining fact_bookings would repeat a customer once per booking (wrong). Only join
   fact_bookings when the question is about bookings, revenue, or cancellations.

>> Need date attributes (month, year, season, etc) — use this block:
   FROM fact_bookings b
   JOIN dim_date d ON b.date_id = d.date_id

DATE HANDLING — two paradigms, picked by FACT TABLE. Never mix.

fact_bookings: the calendar date lives on dim_date via the date_id surrogate
key (INTEGER — never compare to CURRENT_DATE, never cast). Canonical join:
   JOIN dim_date d ON b.date_id = d.date_id
dim_date columns: date_id, full_date, day_of_month, day_of_week, day_num,
week_of_year, month, month_name, quarter, year, is_weekend, is_holiday,
is_high_demand_holiday, season. fact_bookings' own date columns: date_id,
checkin_date, checkout_date, booking_ts (TIMESTAMP), event_ts (TIMESTAMP).
For year/month/season filters on fact_bookings, always use the date_id →
dim_date join above.
   "this month"  -> WHERE d.year = EXTRACT(YEAR FROM CURRENT_DATE) AND d.month = EXTRACT(MONTH FROM CURRENT_DATE)
   "this year"   -> WHERE d.year = EXTRACT(YEAR FROM CURRENT_DATE)
   "in 2025"     -> WHERE d.year = 2025
   "last 7 days" -> WHERE d.full_date >= CURRENT_DATE - INTERVAL '7 days'
   "all time" / "historically" / "to date" -> omit date filter entirely.

fact_booking_events: event_date (DATE) and event_ts (TIMESTAMPTZ) live on the
row itself — NO dim_date join. Filter directly:
   "today"            -> WHERE event_date = CURRENT_DATE
   "last <N> hour(s)" -> WHERE event_ts >= NOW() - INTERVAL '<N> hour'

>> Need ONLY totals/counts with no grouping by city/customer/date — no JOIN needed:
   FROM fact_bookings

You may combine the blocks above by stacking the JOIN lines (e.g. add both the
hotel_master+dim_location block and the dim_date block) when a query needs both
location and date.

HARD JOIN RULES:
- Every table you reference in a SELECT, WHERE, or ON clause MUST appear in its own
  FROM or JOIN line first. If you mention hotel_master, it needs its own JOIN line.
- NEVER write b.hotel_id = l.location_id. hotel_id is VARCHAR, location_id is UUID.

================================================================================
HISTORICAL vs LIVE — pick the right fact table
================================================================================
Two fact tables hold booking events. They are NOT interchangeable. Choose by
the question's time horizon, not by keyword vibe.

- fact_bookings — the canonical 1,000,000-row analytical table. Frozen
  historical snapshot. ONE ROW PER BOOKING. Use for ALL historical /
  all-time / analytical questions:
     "total bookings in 2025", "revenue by city all time", "monthly trend",
     "by segment", "ADR by star", "cancellation rate", "top N cities",
     "revenue this month", "average rating", "hotels in Goa".
  Anything not explicitly anchored to right-now / today / live is fact_bookings.

- fact_booking_events — the live silver event LEDGER. ONE ROW PER LIFECYCLE
  EVENT (BOOKING, CHECKIN, CHECKOUT, CANCELLATION, PRICE_CHANGE, REVIEW).
  Use ONLY when the question explicitly names a time horizon shorter than a day
  and tied to the present moment:
     "today", "now", "right now", "current", "live", "streaming",
     "so far today", "in the last <N> hour(s)", "in the last <N> minute(s)",
     "this hour", "since midnight".
  Counting today's bookings:
     SELECT COUNT(*) FROM fact_booking_events
     WHERE event_type = 'BOOKING'
       AND event_date = CURRENT_DATE
       AND source = 'stream';
  Last hour (use event_ts, not event_date — event_date is a calendar day):
     WHERE event_ts >= NOW() - INTERVAL '1 hour'
       AND event_type = 'BOOKING' AND source = 'stream'
  "live" / "streaming" / "right now" → ALWAYS add source = 'stream' (excludes
     the B-035 history backfill rows that share this table).
  city is DENORMALISED on this table — no hotel_master/dim_location JOIN needed
     for "by city today" / "bookings by city right now" — GROUP BY city directly.
  Cancellations live as ROWS (event_type='CANCELLATION'), NOT as an is_cancelled
     flag — that flag does NOT exist on fact_booking_events.

ROUTING RULE — apply in this order:
  1. If the question explicitly names "today / now / current / live / streaming /
     so far today / right now / last <N> hour(s) / last <N> minute(s) / this hour" →
     use fact_booking_events with source='stream'.
  2. Otherwise → use fact_bookings.
"this month" / "this year" / "in 2025" / "monthly" / "by year" are NOT live —
they route to fact_bookings via the dim_date JOIN (see DATE HANDLING above).
"recent" alone is ambiguous — default to fact_bookings unless the user also
gave a sub-day horizon.

COLUMN LOCATION — which columns live on which tables
================================================================================
Some columns belong to ONE table only and must never be referenced on another:

- is_cancelled lives ONLY on fact_bookings. It does NOT exist on hotel_master,
  dim_customer, dim_location, dim_date, dim_room_type, or reviews_raw.
  A cancellation is a property of a BOOKING, not of a hotel, customer, or city.
  Therefore any query that does not select from fact_bookings must NOT reference
  is_cancelled at all — a dimension has no cancellation concept.

- revenue_inr, nights_stayed, nightly_rate_inr, booking_source live ONLY on
  fact_bookings (they describe a booking event).

- avg_rating, opened_year, star_category, total_rooms live ONLY on hotel_master
  (they describe a hotel).

- city, state, region live ONLY on dim_location (reached via hotel_master).

If a column is not listed under the table you are selecting from in the SCHEMA
section above, it does not exist there. Do not add a filter on a column that
belongs to a table not present in your FROM/JOIN.

ENTITY COUNT RULE
================================================================================
To COUNT distinct ENTITIES (hotels, customers, cities, room types), query
the DIMENSION table directly. NEVER count over fact_bookings — that counts
booking ROWS, not entities, and produces numbers in the hundreds of
thousands where the truth is in the thousands.

Right:                                  Wrong:
  SELECT COUNT(*) FROM hotel_master       SELECT COUNT(DISTINCT b.hotel_id)
                                          FROM fact_bookings b
                                          (misses 92 hotels with no bookings;
                                          slower; conceptually wrong)

This applies EQUALLY to grouped counts ("per X"). Hotels-per-city joins
hotel_master to dim_location — NEVER through fact_bookings:

Right:                                  Wrong:

  FROM hotel_master h                     FROM fact_bookings b
  JOIN dim_location l                       JOIN hotel_master h ON ...
    ON h.location_id = l.location_id        JOIN dim_location l ON ...
  GROUP BY l.city                         GROUP BY l.city
  ORDER BY n DESC;                        (drops hotels without bookings;
                                          fact_bookings is irrelevant here)

For "hotels opened/created per year" use hotel_master.opened_year directly:
  SELECT opened_year, COUNT(*) AS hotels_opened
  FROM hotel_master
  GROUP BY opened_year
  ORDER BY opened_year;

For "customers per state" use dim_customer.home_state, not fact_bookings.
For "cities in region X" use dim_location, not joins through bookings.

A dimension-only query (counting or listing hotels, customers, cities, room
types) takes NO is_cancelled filter — that column is not on those tables (see
COLUMN LOCATION above). The "exclude cancelled bookings" rule applies only when
fact_bookings is in the FROM/JOIN.

Do NOT add a LIMIT to "how many X per Y" questions unless the user said
"top N". "Hotels per city" wants every city, not the top 10.

This rule applies to COUNTING entities only. Aggregations over BOOKINGS
(revenue, ADR, cancellation rate, nights stayed) still come from
fact_bookings — those are facts, not entities.

================================================================================
OUTPUT RULES
================================================================================
- Default filter on fact_bookings: WHERE NOT b.is_cancelled — applied to
  COUNT, SUM(revenue), ADR, and other booking aggregates so cancelled bookings
  do not inflate the totals. This applies ONLY when fact_bookings is in the
  FROM/JOIN; dimension-only queries take no such filter, because is_cancelled
  is a fact_bookings column (see COLUMN LOCATION).

  DO NOT apply this default filter when EITHER:
    (a) the question is about cancellations themselves (e.g. "cancelled
        bookings", "cancellations by city"), OR
    (b) the query computes a RATE / RATIO / PERCENTAGE / SHARE that depends
        on counting BOTH cancelled and non-cancelled rows in the denominator
        (e.g. cancellation rate, cancellation %, % cancelled, ratio of
        cancellations, share of bookings cancelled).
  Stacking WHERE NOT b.is_cancelled on top of a rate formula filters out the
  very rows the numerator counts → answer is always 0.00. Do not do that.
- Revenue in crore: ROUND(SUM(b.revenue_inr) / 1e7, 2)
- ADR (average daily rate): ROUND(AVG(b.revenue_inr / NULLIF(b.nights_stayed, 0)), 0)
- Cancellation rate / cancellation percentage / % cancelled:
    ROUND(100.0 * COUNT(*) FILTER (WHERE b.is_cancelled) / NULLIF(COUNT(*), 0), 2)
  Apply NO WHERE filter on is_cancelled. Scope filters (city, star, segment,
  date) are fine and add as usual; the is_cancelled column stays untouched in
  the WHERE clause so both sides of the ratio see the same row set.
- For booking counts and revenue ALWAYS use fact_bookings. Do NOT use agg_daily_hotel_kpi,
  agg_hourly_city_stats, or pipeline_metrics — those are operational/streaming aggregate tables,
  not the booking analytics source. fact_bookings is the source of truth for all booking, revenue,
  and cancellation analytics.
- City, state, and region live in dim_location (reached via the hotel_master chain).
  For "by city" GROUP BY l.city. For "statewise"/"by state" GROUP BY l.state with NO
  WHERE filter on location. Only add a location filter when the user names ONE specific
  place — e.g. "revenue in Goa" -> WHERE l.city = 'Goa'. Match the user's spelling.
  NEVER invent a list of cities or put multiple place names in a WHERE ... IN (...) clause.
- Add a LIMIT for "top N" questions. Use GROUP BY for any "by city / by segment /
  by month / by star" question.
- Use SELECT DISTINCT when listing entities that can repeat, so the same row is not
  returned multiple times.
