01 The Real-World Problem

New to hotel industry data? — Key terms explained EXPAND · 6 TERMS
RevPAR

Revenue Per Available Room = ADR × Occupancy Rate. The gold-standard hotel KPI — captures pricing power and utilisation in one number.

ADR

Average Daily Rate = total room revenue ÷ rooms sold. Measures pricing power independently — a hotel can have high ADR but terrible occupancy.

Occupancy Rate

Rooms occupied ÷ rooms available. India peak season (Nov–Jan): 70–80%. Monsoon (Jun–Sep): 30–40%. Varies wildly by tourism type.

OTA

Online Travel Agency — MakeMyTrip, OYO, Booking.com. Account for ~60% of Indian hotel bookings. The booking_source field in our schema tracks which OTA drove each reservation.

Tumbling Window

A streaming concept: fixed non-overlapping time buckets. A 1-hr tumbling window opens at :00, collects events, closes at :59, outputs one record per city, then repeats. No overlap.

Lambda Architecture

Two parallel layers: a speed layer (stream consumer, sub-second) for live data, and a batch layer (DWH) for accurate historical data. TravelLens uses both — queries hit whichever is right for their latency need.

India's tourism sector is worth ₹2.3 lakh crore. It spans 10,000+ registered hotels and 1.4 billion domestic tourist trips annually. A single peak-season weekend at a coastal destination like Goa generates more booking and pricing events than most mid-size SaaS companies handle in a month. Yet the people who run these properties — revenue managers, GMs, state tourism boards — are making billion-rupee decisions from last night's Excel export. The data exists. The answers don't.

02 Executive Summary

What TravelLens builds, what problem it solves, and what you learn by building it — in one page.

What it is

A real-time hotel intelligence platform covering the full data engineering stack: event streaming (Kafka + Python consumer), a 14-table star schema warehouse (Postgres + pgvector), an S3 data lake with hotel CSVs and 30K+ review JSONs, a Text-to-SQL engine running a local LLM (Ollama + Qwen2.5-Coder-7B), and an HTML dashboard output layer. India's hotel operators have no way to query their own operational data in real time. Revenue decisions lag 12–18 hours. Guest complaint trends take days to surface. State tourism data is 18 months old. TravelLens ingests, aggregates, and exposes all of this to a plain-English query interface.

Event-time semantics and tumbling windows. Star schema design decisions. S3 partitioning strategy. Text-to-SQL prompt engineering with schema context. 03 Design Philosophy

Three principles that shaped every architectural decision in TravelLens.

Naturally streaming domain

Booking events, check-ins, price changes happen continuously. The streaming layer is not forced here — a hotel in peak season generates 200–500 events per hour. Tumbling windows turn that into actionable occupancy aggregates without batch delay. This is the domain that makes a real-time pipeline genuine, not bolted-on.

Two AI query paths, not one

Structured questions ("top 5 cities by RevPAR") route to Text-to-SQL — a local Qwen2.5-Coder-7B model generates SQL, the DB returns rows. Review qualitative questions ("what do guests complain about?") bypass SQL entirely and use pgvector cosine similarity over embeddings, then the same local LLM summarises the matching reviews. One system demonstrates two fundamentally different AI patterns, both running offline.

Output that travels without infrastructure

A revenue manager in Jaipur shouldn't need Tableau or a VPN to read a report. Every query result is a self-contained HTML file — opens on any device, shareable over WhatsApp. This is the right output format for India's hospitality market, not a dashboard requiring internet and login.

Hybrid infrastructure — why each component earns its place

AWS S3 (Data Lake)

One bucket travellens-data with 4 logical prefixes: raw/ hotel CSVs, reviews/ JSONs + embeddings, reference/ lookups, and processed/ stream Parquet archives + dashboard HTML. Immutable, versioned, cheap. Bronze→Silver ETL produces Parquet that gets loaded into Postgres for fast querying.

Postgres + pgvector (Warehouse)

Production-grade relational database — handles concurrent writers (streaming consumer + Airflow batch jobs + ad-hoc queries) without lock contention. pgvector extension stores 384-dim review embeddings natively with cosine similarity indexing. JSONB handles amenities arrays with indexed queries.

Python Stream Consumer

A ~500-line Python consumer reads Kafka events through a six-gate validator (JSON parse, schema checks, late-event guard), maintains in-memory windowed state keyed by city, and flushes closed windows to a dual sink (Postgres upsert + S3 Parquet archive). Failed events are quarantined to dedicated S3 prefixes (malformed_events/, late_events/) for operational triage. Event-time watermark grace absorbs network delay from rural hotel properties. Originally prototyped with PyFlink — see "Streaming Implementation" note in the datamodel doc.

Ollama + Qwen2.5-Coder-7B (AI Layer)

A 7B-parameter code-specialized LLM runs locally via Ollama, GPU-accelerated on Nvidia/Metal. Generates SQL from natural language using a system prompt with full schema DDL, India context, and few-shot examples. Same model summarises top-K reviews after pgvector retrieval. Zero API cost, sub-second latency on RTX 3070, fully offline.

05 Data Schema — 14 Tables

3 fact tables, 5 dimension tables, 4 reference tables, 2 aggregation tables written by the stream consumer and Airflow batch jobs. Every table has a reason to exist. Card view here; datamodel.md has the full column-by-column spec.

Why Star Schema — not a flat table, not a document store

Flat Table ✗ Rejected
A single denormalised CSV repeats hotel name, star category, city, and state on every booking row. At 1M bookings across 2K hotels, that's 500 redundant copies of every hotel attribute on average. Updating one hotel's star category means touching thousands of rows — write amplification that guarantees stale data. Text-to-SQL accuracy also drops significantly because the model must navigate ambiguous column names.
Document Store ✗ Rejected
MongoDB allows flexible schemas but hotel operational queries are never flexible — they're aggregations across known dimensional slices (city × star_category × date). Document stores force deserialization overhead for columnar aggregations (COUNT, SUM, AVG, GROUP BY) that Postgres handles efficiently with proper indexing, while still supporting the ACID guarantees needed for transactional updates.
Star Schema
fact_bookings stores what happened (high cardinality — millions of rows). Dimensions store context (low cardinality — thousands of rows). Postgres uses indexes to skip irrelevant rows efficiently. Text-to-SQL accuracy is higher because FK relationships are explicit and joins are single-level. 90% of queries touch fact_bookings with one or two simple joins.

Why 1 bucket + prefixes (not 4 buckets)?

At portfolio scale, prefixes give the same logical separation as separate buckets without the operational overhead. One bucket means one IAM policy to manage, one lifecycle config, one billing line. Production-grade data lakes often DO split into multiple buckets — typically when different data classes need different IAM, different KMS keys, or different replication targets. None of those apply here. Choosing simplicity is the right call when the cost is zero.

Why year=/month= partition key?

Hotel ops queries are almost always time-bounded — "this month", "last quarter", "peak season". Partitioning by year=/month= lets the ETL job and Athena queries push the filter down to S3, reading only the relevant monthly files instead of scanning the full lake.

06 Streaming Pipeline

The stream consumer reads the booking-events Kafka topic, validates every event through a six-gate validator, keys the stream by city, applies tumbling event-time windows, and writes city stats to both Postgres and S3. Failed events (malformed schema or late arrivals) are quarantined to dedicated S3 prefixes for operational triage. This is the speed layer — live data, updated every window, with explicit failure observability.

Why event time, not processing time?

A hotel in rural Rajasthan may have intermittent connectivity. A burst of 40 booking events generated at 14:00 might reach the Kafka broker at 14:23. Processing-time windows would assign these to the wrong hour — or split them across two windows. Event-time watermarks tell the consumer: wait a configurable grace period (5 min in production, 30s in dev) after the window closes before producing the aggregate, to absorb late arrivals. The output is correct. The latency cost is the grace period — acceptable for hourly aggregates.

Six-gate failure handling — nothing is silently dropped

Every event passes through six explicit gates. Anything that fails a gate is routed to a dedicated S3 prefix with full diagnostic context (raw value, Kafka offset/partition, consumer timestamp). Per-reason counters surface non-zero malformed totals in the consumer's shutdown summary as explicit team TODOs.

1Unparseable JSONmalformed_events/ 2Missing required fieldmalformed_events/ 3Unknown event_type (not BOOKING/CANCELLATION/CHECKIN/PRICE_CHANGE)malformed_events/ 4Unknown city (not in dim_location)malformed_events/ 5Unparseable event_ts (not ISO 8601)malformed_events/ 6Late event (window already closed past watermark)late_events/

Why two prefixes: malformed events need human triage (someone broke the producer schema); late events are mechanically recoverable (Phase 6 reconciler will additively merge them back into agg_hourly_city_stats). Different recovery paths, different sinks.

1
Kafka Source — consume booking events
A Python producer publishes JSON events to the booking-events topic at a configurable rate (default 50 evt/sec, configurable via --rate). Each event carries event_id, event_type (BOOKING / CANCELLATION / CHECKIN / PRICE_CHANGE), hotel_id, city, revenue_inr, and event_ts. Hotel IDs are seeded from Phase 1's hotel_master so joins resolve. The producer can inject chaos (--malformed-pct, --late-pct, --chaos-seed) for reproducible failure testing.
2
Validate, accumulate, watermark — in-memory windowed state
Each event passes through the six-gate validator. Valid BOOKING / CANCELLATION events accumulate into a dict keyed by (window_start, city). Each city accumulates independently. The watermark (max_event_ts − 5 min) advances as new events arrive. When a window's end falls below the watermark, the consumer flushes one row per city: total_bookings, total_revenue_inr, avg_occupancy_rate, cancellation_rate.
3
Dual sink — Postgres agg table + S3 Parquet archive
Every flushed window writes to both sinks. Postgres receives an UPSERT on agg_hourly_city_stats(city, window_start) — what the Text-to-SQL engine queries for live data. S3 receives a Parquet file at a Hive-partitioned key — the immutable archive for downstream batch consumers (DuckDB, Spark, Athena). Both sinks are idempotent (Postgres ON CONFLICT, deterministic S3 keys), so re-flushes don't double-count.

Architect's Note — Why pure Python, not PyFlink?

The original blueprint specified PyFlink. We pivoted after PyFlink 1.18's Python DataStream API showed serialization issues on Windows + Python 3.11 (apache-beam coder errors, JNI gateway crashes during graceful shutdown). Three iterations of type-system patches did not resolve them.

At 50 events/sec on a single node, the full Flink runtime is over-provisioned anyway. The architectural pattern stays identical — Kafka source, keyed-by-city aggregation, event-time watermarking, dual sink, side-output for late events. We just implement it in pure Python instead of routing through Flink's Python wrapper. Production path at 5K+ evt/sec: AWS Managed Flink with the Table API. Same shape, different runtime.

Sample — natural language → LLM-generated SQL
▶"Which cities had occupancy above 80% last December?"
Generated SQL
SELECT l.city, AVG(k.occupancy_rate) AS avg_occ
FROM agg_daily_hotel_kpi k
JOIN dim_hotel h ON k.hotel_id = h.hotel_id
JOIN dim_location l ON h.location_id = l.location_id
JOIN dim_date d ON k.kpi_date = d.full_date
WHERE d.month_name = 'December' AND EXTRACT(YEAR FROM d.full_date) = 2024
GROUP BY l.city HAVING AVG(k.occupancy_rate) > 80
ORDER BY avg_occ DESC;
▶"Show budget hotels in Goa with rating above 4.0"
Generated SQL (joins ref_price_tiers)
SELECT h.hotel_name, h.avg_rating, h.total_rooms, pt.tier_name
FROM dim_hotel h
JOIN dim_location l ON h.location_id = l.location_id
JOIN dim_room_type rt ON h.hotel_id = rt.hotel_id
JOIN ref_price_tiers pt ON rt.price_tier = pt.tier_id
WHERE l.city = 'Goa' AND h.avg_rating > 4.0
  AND pt.tier_name = 'Budget'  -- resolved from ref_price_tiers, <₹2000
ORDER BY h.avg_rating DESC;
What the system prompt must contain — and why it matters

Every LLM call to Qwen2.5-Coder-7B includes: (1) Full schema DDL — every table, column, type, and FK relationship. (2) India-specific context — currency as INR, common city names, that "budget" means under ₹2,000/night. (3) 5 few-shot examples of natural language → correct SQL pairs. (4) A hard constraint: only generate SELECT statements. Without the schema DDL, the model invents column names. Without few-shot examples, it gets JOIN direction wrong for FKs. Without the India context, "budget hotel" generates an arbitrary price filter. Prompt engineering is what makes Text-to-SQL reliable — not the model alone. After generation, every query is parsed with sqlparse and validated against the live schema before execution.

08 Review Intelligence — Semantic Search

The review path answers qualitative questions that SQL cannot. "What are guests complaining about?" is not a GROUP BY query. It requires understanding meaning across 30,000 free-text reviews and surfacing the dominant themes — in seconds.

Why not just full-text search?

Full-text search for "cleanliness"
"The room was clean and tidy." ✓ matched
"Housekeeping was disappointing." ✗ missed
"The bathroom had an unpleasant smell." ✗ missed
"Unhygienic facilities throughout." ✗ missed

3 of 4 relevant reviews missed — keywords don't match.
Semantic search for "cleanliness"
"The room was clean and tidy." ✓ matched (similarity: 0.92)
"Housekeeping was disappointing." ✓ matched (0.84)
"The bathroom had an unpleasant smell." ✓ matched (0.81)
"Unhygienic facilities throughout." ✓ matched (0.78)

All 4 found — meaning, not just keywords.
Step 1 — Detect
Query routing

Keyword detection: "complain", "feedback", "like", "guests say", "think about". If triggered → semantic path. If not → SQL path.

Step 2 — Embed
Query vectorisation

Run the question through all-MiniLM-L6-v2. Produces a 384-dim vector in the same space as the pre-computed review embeddings.

Step 3 — Filter + Search
pgvector cosine

Filter by hotel.city + hotel.star_category from query context. Run pgvector cosine similarity (<=> operator) against review embeddings. Return top-20 most semantically similar reviews.

Step 4 — Summarise
Local LLM theme extraction

Pass top-20 review chunks to Qwen2.5-Coder-7B: "Identify the top 3 complaint themes. Be specific." Returns structured theme breakdown in plain English. Runs locally on the same GPU as the SQL generation model.

Real data — not simulated reviews

The reviews_raw table is seeded from real public datasets on Kaggle: MakeMyTrip Hotel Reviews India and OYO Hotels India — sampled down to 30K reviews covering 2,000 hotels. These are actual guest reviews with real complaint patterns — WiFi issues, housekeeping inconsistency, food quality at budget properties, noise problems at urban hotels. The semantic search works on real signal. Search "MakeMyTrip hotel reviews India Kaggle" and "OYO hotel reviews Kaggle" to find both datasets.

12 Known Limitations & What I'd Do Differently

Honest technical self-critique. A portfolio project built alone in 21 days trades completeness for demonstrability. These are the known gaps:

Limitation Why it exists What I'd do in production
Simulated streaming events Kafka events come from a Python simulator, not a real hotel PMS. Schema and volume are realistic but the data is synthetic — no live property feeds. Replace the simulator with Kafka Connect connectors pulling from actual hotel PMS webhook APIs (OYO, MakeMyTrip partner APIs). The stream consumer is unchanged — only the producer differs. For higher event rates (5K+/sec) the production path moves to AWS Managed Flink with Table API.
No SQL hallucination guard Qwen2.5-Coder-7B occasionally generates plausible-but-wrong column names for ambiguous queries — more often than Claude would. The system prompt has a hard SELECT-only constraint, but no schema validation on the output by default. Parse the generated SQL with sqlparse, validate all table and column references against the live schema, and reject the query before execution if any reference is invalid.
pgvector with IVFFlat index (not HNSW) Review embeddings sit in Postgres as vector(384) columns. IVFFlat indexing is fast enough at 30K reviews. Recall and latency degrade past ~1M vectors. Switch to HNSW indexing (pgvector 0.5+) for better recall at scale, or move to a dedicated vector store (Pinecone, Weaviate) past 5M+ vectors.
No Airflow DAG in the first build The daily batch load (S3 → Postgres dim tables, agg_daily_hotel_kpi refresh) is run manually. A cron + Python script substitutes for the demo build. Add an Airflow DAG with task dependencies, retry logic, SLA alerts, and backfill support for missed runs. Critical once the pipeline runs in production for multiple properties.

Phase 1 Postgres Foundation — Step-by-Step Guide
Phase 1 — Postgres Foundation

Objective. Stand up a Postgres 16 database in Docker with the pgvector extension, create the 14-table TravelLens schema, and bulk-load all 13 source CSVs from data/ into the right tables with foreign-key integrity verified.

Prerequisites
  • Docker 24.x or newer running
  • Python 3.11+ with active venv; psycopg2-binary, python-dotenv installed
  • data/ with 13 source files (12 CSVs + 1 JSON)
  • .env with POSTGRES_* credentials and DATA_DIR
Deliverables
  • docker/postgres.Dockerfile + docker-compose.yml
  • db/schema.sql — 14 tables, no inline indexes
  • scripts/load_to_postgres.py — COPY FROM STDIN bulk loader
  • scripts/validate_load.py — 20-check integrity validator
Build Steps
1 Write the Postgres Dockerfile

Base image: postgres:16. Install postgresql-16-pgvector apt package. UTF-8 locale init args.

2 Write docker-compose.yml

Single postgres service. Mount ../data:/data:ro and ../db:/db:ro read-only so the loader can COPY directly from container-internal paths. Healthcheck via pg_isready.

3 Start the container and enable pgvector

docker compose up -d --build. Then: CREATE EXTENSION IF NOT EXISTS vector;. Verify with \dx vector.

4 Apply schema.sql (14 tables)

Creation order matters for FKs: reference → dimensions → facts → aggregates. Critical column specs: reviews_raw.embedding is vector(384), hotel_master.amenities is JSONB, agg_hourly_city_stats has PK (city, window_start). No inline indexes — those go post-load for speed.

5 Write the loader

Idempotent: TRUNCATE CASCADE RESTART IDENTITY before insert. Disable FK checks with SET session_replication_role = replica; during load; re-enable after — if this fails, an orphan exists. Use cursor.copy_expert("COPY {} FROM STDIN WITH (FORMAT csv, HEADER true, NULL '')"). Load in dependency order (12 CSVs). Create indexes post-load. Wrap in one transaction; rollback on any exception.

6 Write the validator (20 checks)

Row-count checks per table (4 / 147 / 2557 / 20000 / 2000 / 5542 / 1000000 / 86650 / 30000). Orphan checks (LEFT JOIN, count IS NULL == 0). Business-logic checks: no negative revenue on non-cancelled bookings, cancellation rate 8–15%, ratings 1.0–5.0, total revenue 1800–2500 cr.

Acceptance Tests
  • Container travellens-postgres shows status healthy
  • Schema has exactly 14 base tables
  • pgvector extension installed
  • fact_bookings has exactly 1,000,000 rows
  • reviews_raw has exactly 30,000 rows
  • Zero FK orphans across all fact tables
  • python scripts/validate_load.py reports PASSED: 20 / 20
Do Not
  • Do not use INSERT INTO ... VALUES for bulk loading — only COPY FROM STDIN
  • Do not create indexes inside schema.sql — they go in the post-load step
  • Do not generate embeddings (Phase 3 work — reviews_raw.embedding stays NULL after Phase 1)
  • Do not skip the FK re-enable step in the loader
  • Do not modify any file in data/

Phase 2 Streaming Pipeline — Step-by-Step Guide
Phase 2 — Streaming Pipeline

Objective. Build a pure-Python Kafka consumer that reads booking events, validates them through a six-gate validator, aggregates them by city in tumbling event-time windows, and dual-sinks each window to Postgres + S3 Parquet. Quarantine failures to dedicated S3 prefixes so nothing is silently dropped.

Prerequisites
  • Phase 1 accepted — 20/20 validation checks pass, 14 tables loaded
  • docker ps shows travellens-postgres healthy
  • data/booking_events_seed.json exists
  • .env has KAFKA_BOOTSTRAP, S3_BUCKET, AWS_*
Deliverables
  • docker-compose.yml — extended with Kafka + Zookeeper + MinIO
  • scripts/init_s3_buckets.py — idempotent bucket bootstrap
  • scripts/kafka_event_producer.py — chaos-injection CLI
  • scripts/stream_consumer.py — six-gate validator, dual sink
Build Steps
1 Extend docker-compose.yml with Kafka + Zookeeper + MinIO

Add three services to the existing Postgres-only compose. Kafka on localhost:9092 with auto-topic-create enabled. MinIO on localhost:9000 (S3 API) / localhost:9001 (console). Bring up: docker compose up -d. All four containers should show Up.

2 Write init_s3_buckets.py

Creates travellens-data bucket and four prefixes (raw/, reviews/, reference/, processed/). Idempotent. Verify with mc ls local/travellens-data/.

3 Write the producer

CLI flags: --rate (default 50), --duration (0=forever), --malformed-pct, --late-pct, --chaos-seed. Five chaos generators (one per consumer reason code). Critical: empty strings are removed from _corrupt_unparseable_ts and _corrupt_unknown_event_type — they would trigger missing_field instead via fail-fast validation. Value serializer must pass bytes through unchanged so unparseable-JSON chaos reaches the wire raw.

4 Write the consumer

CLI flag: --max-runtime (0=forever, default; non-zero=bounded run). Event loop order (gates):

  1. Gate 1 JSON parse (robust deserializer returns sentinel on failure)
  2. Gate 2 Schema validation (returns one of: missing_field, unknown_event_type, unknown_city, unparseable_event_ts)
  3. Gate 3 Event-type filter (silent skip for CHECKIN, PRICE_CHANGE — not malformed)
  4. Parse event_ts (safe after validation)
  5. Gate 4 Late-event guard (window_end_secs < watermark_secs) — this must fire BEFORE accessing state[key], or defaultdict resurrects flushed windows and corrupts aggregates
  6. Accumulate into state[key]

Postgres sink: UPSERT on (city, window_start). S3 sink: Hive-partitioned Parquet at processed/agg/hourly_city_stats/year=YYYY/month=MM/day=DD/hour=HH_{city}.parquet. Run summary on shutdown prints four counters with malformed_by_reason breakdown; non-zero malformed counts surface as explicit "TODO for team" lines.

5 Test 1 — clean baseline (no chaos)

Reset Kafka offsets to latest (mandatory between runs). Truncate agg_hourly_city_stats. Launch consumer with --max-runtime 420 and producer with --rate 50 --duration 300. Pass criteria: 15,000 events consumed, 44 windows flushed (44 cities × 1 hour), 0 malformed, 0 late, Postgres = 44 rows.

6 Test 2 — chaos enabled

Same setup, producer with --malformed-pct 5 --late-pct 2 --chaos-seed 42. Pass criteria: producer total malformed = consumer total malformed (exact). Per-reason distributions match within ±10. Postgres = 44 rows. Sample malformed quarantine file exists in s3://travellens-data/malformed_events/.

Lessons Learned
  • Kafka offsets are sticky. auto_offset_reset="latest" only applies on first connect. Reset explicitly between test runs.
  • Windows cross-process SIGINT is fragile. Use --max-runtime for bounded runs instead of trying to send signals.
  • defaultdict resurrects flushed windows. Late guard MUST fire before state[key] access — silently created zero state corrupts aggregates on re-flush.
  • Empty strings are ambiguous corruption. Removed from _corrupt_unparseable_ts and _corrupt_unknown_event_type because they hit missing_field via fail-fast first.
  • Schema introspection is mandatory. Don't write SQL from memory — cities are in dim_location, not hotel_master.

Phase 3 Embeddings + pgvector — Step-by-Step Guide
Phase 3 — Embeddings + Semantic Search Foundation

Objective. Populate the embedding vector(384) column on all 30K rows in reviews_raw using all-MiniLM-L6-v2. Build an IVFFlat cosine index. Foundation for Phase 4 semantic search.

Prerequisites
  • Phase 2 complete — Docker stack running (Postgres, Kafka, MinIO)
  • reviews_raw has 30K rows, embedding vector(384) column all NULL
  • CUDA: python -c "import torch; print(torch.cuda.is_available())" → True
  • sentence-transformers==3.0.1, pgvector==0.3.6, tqdm installed
Deliverables
  • scripts/generate_embeddings.py — idempotent batch embedding job
  • 30K embeddings in reviews_raw.embedding · IVFFlat index idx_reviews_embedding
Key Design Decisions
  • all-MiniLM-L6-v2 — 384-dim, paraphrase-trained. "Room was filthy" and "hygiene was terrible" cluster together. ~90MB, offline, ~1,800 reviews/sec on RTX 3070.
  • Idempotent via WHERE embedding IS NULL — crash and restart picks up where it left off. Future reviews auto-handled.
  • Truncate at 1,000 chars, never skip — skipping leaves NULL embeddings invisible to search.
  • IVFFlat built last, lists=30 — k-means requires data first. 30 = rows/1000 rule of thumb.
Build Steps
1 Verify CUDA then run the job

python scripts/generate_embeddings.py — watch truncation count in log (~5% expected). Index builds automatically at end.

2 Acceptance tests in psql

SELECT COUNT(*) FROM reviews_raw WHERE embedding IS NULL; → 0. Dimensionality: SELECT array_length(embedding::float4[], 1) FROM reviews_raw LIMIT 1; → 384.

3 Smoke test

python scripts/semantic_playground.py — type "AC not working" — verify results mention cooling/heat even without those exact words.

Explore the Data

Use psql for any query using the <=> operator — DuckDB does not proxy pgvector. For other queries use DuckDB UI: attach Postgres in first cell (context = memory), then add USE travellens_postgres.public; as the first line of every subsequent cell.

  • Coverage: SELECT COUNT(*), COUNT(embedding), ROUND(100.0*COUNT(embedding)/COUNT(*),2) AS pct FROM reviews_raw;
  • Length distribution + truncation count: SELECT MIN(LENGTH(review_text)), ROUND(AVG(LENGTH(review_text))), MAX(LENGTH(review_text)), COUNT(*) FILTER (WHERE LENGTH(review_text)>1000) AS truncated FROM reviews_raw;
  • Rating distribution: SELECT ROUND(rating) AS stars, COUNT(*) FROM reviews_raw GROUP BY stars ORDER BY stars;

Phase 4 — AI Layer

Objective. Dual-path natural language query engine. SQL questions → Ollama generates SQL → execute against Postgres. Review questions → embed query → pgvector cosine search → Ollama summarises themes. Entry point: python ai/main.py "your question".

Prerequisites

Key Design Decisions
